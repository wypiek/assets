How special.png works

special.png is a polyglot: one file that is valid as three formats at once. Renaming it does not change any bytes. It only changes which program opens it, and each program reads the part it understands and ignores the rest.

NameOpened byWhat you see
.pngimage viewer"Hey you! Save this image and rename it to .pdf"
.pdfPDF reader"Great! Now rename it to .html"
.htmlweb browserredirect to https://twitter.democrat

1. The PNG part

A PNG file is an 8-byte signature followed by chunks. Each chunk is:

[length: 4 bytes] [type: 4 letters] [data] [CRC: 4 bytes]

The chunks that matter are IHDR (size and colour type), IDAT (the compressed pixels) and IEND (end of file). A chunk type that starts with a lowercase letter is "ancillary": if a viewer doesn't recognise it, it skips it using the length field. So we can hide anything in custom chunks, and every image viewer will still show the first picture.

2. The file layout

offset   chunk   contents
0        -       PNG signature  89 50 4E 47 0D 0A 1A 0A
8        IHDR    1280x1280, RGB
33       pdFh    HTML redirect + start of the PDF
354      IDAT    the PNG picture (step 1)
147781   pdFt    the rest of the PDF (with the step 2 picture)
241059   IEND    end of PNG

pdFh and pdFt are made-up chunk names. The viewer skips them, but the HTML and PDF readers don't care about chunks at all and just see the bytes inside.

3. The PDF part

PDF readers don't require %PDF to be at byte 0. Most of them search the first 1024 bytes for it. In this file it is at byte 295, inside pdFh.

The PNG picture sits between the two PDF chunks, so the PDF has to step over it. The pdFh chunk ends by opening a dummy object:

%PDF-1.4
1 0 obj
<< /Length 147439 >>
stream

That /Length is exactly the number of bytes up to the start of the pdFt data: the CRC of pdFh, the whole IDAT chunk, and the length and type of pdFt. The PDF reader treats all of that as the content of an unused object and ignores it.

The pdFt chunk then begins with endstream endobj and contains the real PDF: a catalog, one page, the "rename it to .html" picture as a JPEG, the cross-reference table and %%EOF. Only the 12-byte IEND chunk comes after it, so readers that look for %%EOF near the end of the file still find it.

The cross-reference offsets are counted from %PDF, not from byte 0. This matches how Acrobat and Chrome handle a header that doesn't start the file. Readers that disagree rebuild the table themselves.

4. The HTML part

When a local file ends in .html, the browser treats it as HTML whatever it contains. Browsers are very forgiving: the PNG bytes before the first tag are just shown as junk text. Also inside pdFh, before the PDF header, is:

<html><head>
<meta charset="iso-8859-1">
<meta http-equiv="refresh" content="0;url=https://twitter.democrat">
<script>location.replace('https://twitter.democrat')</script>
<style>html,body{background:#fff;color:#fff;overflow:hidden}</style>
</head><body><!--
  • The script redirects immediately. The meta refresh is a backup if scripts are off.
  • The iso-8859-1 charset makes every byte a valid character, so the binary data can't break parsing.
  • White text on white hides the junk for the moment before the redirect.
  • <!-- opens a comment so the rest of the file (the image and PDF data) is not rendered as text.

5. Why there is no .gif step

A PNG must start with 89 50 4E 47 and a GIF must start with GIF89a. A file has only one byte 0, so it can't be both. Most image viewers also check the content rather than the name, so a PNG renamed to .gif would show the same picture as the .png step.

6. Building it

python3 build_polyglot.py step1.png step2.png special.png https://twitter.democrat

The script re-encodes step1.png into chunks it controls, converts step2.png to a JPEG for the PDF page, works out the /Length and cross-reference offsets, and writes the chunks in the order shown above with correct CRCs.
