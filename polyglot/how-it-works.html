How special.png works

special.png is a polyglot: one file that is valid as several formats at once. Renaming it does not change any bytes. It only changes which program opens it, and each program reads the part it understands and ignores the rest.

NameOpened byWhat you see
.pngimage viewer"Hey you! Save this image and rename it to .pdf"
.pdfPDF reader"Great! Now rename it to .html"
.htmlweb browser"Now remove the letter l from html."
.htmweb browserthis page

1. The PNG part

A PNG file is an 8-byte signature followed by chunks. Each chunk is:

[length: 4 bytes] [type: 4 letters] [data] [CRC: 4 bytes]

The chunks that matter are IHDR (size and colour type), IDAT (the compressed pixels) and IEND (end of file). A chunk type that starts with a lowercase letter is "ancillary": if a viewer doesn't recognise it, it skips it using the length field. So we can hide anything in custom chunks, and every image viewer will still show the first picture.

2. The file layout

offset   chunk   contents
0        -       PNG signature  89 50 4E 47 0D 0A 1A 0A
8        IHDR    1280x1280, RGB
33       pdFh    HTML loader + start of the PDF
378      IDAT    the PNG picture (step 1)
147805   pdFt    the rest of the PDF: both HTML pages, then the step 2 picture
(end)    IEND    end of PNG

pdFh and pdFt are made-up chunk names. The viewer skips them, but the HTML and PDF readers don't care about chunks at all and just see the bytes inside.

3. The PDF part

PDF readers don't require %PDF to be at byte 0. Most of them search the first 1024 bytes for it. In this file it is at byte 319, inside pdFh.

The PNG picture sits between the two PDF chunks, so the PDF has to step over it. The pdFh chunk ends by opening a dummy object:

%PDF-1.4
1 0 obj
<< /Length 147439 >>
stream

That /Length is exactly the number of bytes up to the start of the pdFt data: the CRC of pdFh, the whole IDAT chunk, and the length and type of pdFt. The PDF reader treats all of that as the content of an unused object and ignores it.

The pdFt chunk then begins with endstream endobj and contains the real PDF: an unused object holding the two HTML pages, a catalog, one page, the "rename it to .html" picture as a JPEG, the cross-reference table and %%EOF. Only the 12-byte IEND chunk comes after it, so readers that look for %%EOF near the end of the file still find it.

The cross-reference offsets are counted from %PDF, not from byte 0. This matches how Acrobat and Chrome handle a header that doesn't start the file. Readers that disagree rebuild the table themselves.

4. The HTML part

When a local file ends in .html or .htm, the browser treats it as HTML whatever it contains. Browsers are very forgiving: binary bytes are just shown as junk text, and any tags found among them still work. Inside pdFh, before the PDF header, is a small loader:

<html><head>
<meta charset="iso-8859-1">
<style>body{visibility:hidden}</style>
<script>
addEventListener("DOMContentLoaded", function () {
  var e = document.getElementById(/\.htm$/i.test(location.pathname) ? "x" : "m");
  document.documentElement.innerHTML = e.textContent;
})
</script>
</head><body>
  • The iso-8859-1 charset makes every byte a valid character, so the binary data can't break parsing.
  • visibility:hidden hides the junk text while the file loads.
  • Once the whole file is parsed, the script picks a page and replaces everything with it.

The two pages are stored near the start of pdFt, inside an unused PDF object, as

<script type="text/plain" id="m"> ...the "remove the letter l" page... </script>
<script type="text/plain" id="x"> ...this page... </script>

A script with type="text/plain" isn't run. The browser just keeps its text, which the loader reads with textContent.

5. .html vs .htm

Browsers treat .html and .htm exactly the same, so the file can't tell them apart by how it's parsed. Instead, the loader looks at its own address: location.pathname is the path of the open file, like /Users/you/Downloads/special.htm. If it ends in .htm it shows this page; otherwise it shows the message telling you to remove the l.

6. Why there is no .gif step

A PNG must start with 89 50 4E 47 and a GIF must start with GIF89a. A file has only one byte 0, so it can't be both. Most image viewers also check the content rather than the name, so a PNG renamed to .gif would show the same picture as the .png step.

7. Why it breaks when re-saved

Chat apps, photo apps and "Save image" often decode the picture and save a fresh PNG or JPEG. That keeps the pixels but drops unknown chunks, so the PDF and HTML parts disappear. Share the file as a file attachment or inside a .zip.

8. Building it

python3 build_polyglot.py step1.png step2.png special.png

The script re-encodes step1.png into chunks it controls, converts step2.png to a JPEG for the PDF page, inserts the HTML loader and pages, works out the /Length and cross-reference offsets, and writes the chunks in the order shown above with correct CRCs.
